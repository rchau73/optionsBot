# optionsBot monitor (frontend)

A **read-only, single-page live monitor** for the bots: what each strategy holds, what it just did and how it is doing, refreshed every second. All UI documentation lives here; the backend docs only describe the API.

> Educational study of an automated trading system — not investment advice. The monitor is meant for **Deribit testnet** first.

## How it works

```
browser ──1 s polls──▶ Next.js server ──read-only proxy──▶ bot API (Go, internal/api)
                       /api/bots/<bot>/<endpoint>           /api/status · positions · orders · pnl · pnl/history · events · account · trades · summary · performance · income · strangles/payoff · explain
```

- Each bot exposes a read-only JSON API when `BOT_API_ADDR` is set. It is built from the bot's in-memory state — **no Deribit calls, no order endpoints**.
- The browser talks only to the Next.js server, which forwards an allow-list of GET endpoints (`lib/bots.js`). Bot URLs are configured with `BOT_APIS` and never reach the browser.
- Events are fetched incrementally (`/events?since=<seq>`); a bot restart is detected and the feed resumes.
- Every item of `/api/events` and `/api/trades` carries `plain` (#201): one sentence in everyday words — what happened, why, what follows — from the bot's catalogue (`internal/api/explain.go`; the same words as `last_action.reason`). A journal value the catalogue does not know yet gets a generic sentence beginning "The bot recorded a step that has no plain-words explanation yet". The Activity feed and the trade history lead with it (#287, "What you see"); every other field is unchanged.
- `GET /api/status` carries, for the overview's regime chart (#394): `sma.candles` — `[{date (UTC day, YYYY-MM-DD), open, high, low, close}]`, oldest first, the last 60 completed days of the perpetual and today's live candle (its high and low follow the prices the bot pushes; the day roll commits it), from the daily history the bot already loads at startup — no new Deribit call; `[]`/null before any history; `median_flip` (the bias window's median flip under `gex_direction: bias`, 0 otherwise); `gex_as_of` (when the GEX snapshot behind `market` was computed, null before the first); with `flip_buffer_pct` and `market.gamma_flip` as before.
- `GET /api/summary` (#177; in the proxy allow-list since #246, readable by any signed-in role, shown as the investor summary) answers a holder's four questions in one call. Coin amounts are in `underlying` (BTC or ETH), USD at today's `spot` unless said otherwise:
  - `holding` — `strangles`, `legs`, `calls`, `puts`, `notional_coin`, `notional_usd`, `nearest_expiry` and `nearest_dte` (null with no legs), `nearest` (#320: `{expiry, put_strike, call_strike}` — the highest short put and the lowest short call on the nearest expiry, a side with no short leg null; null with no legs), `coin`.
  - `income` — `months`: the last 6 UTC calendar months, oldest first, the current one last, each `{month: "YYYY-MM", realised_coin, realised_usd, closes}` (journal closes net of fees; USD at each close's spot; a month without closes is zeros) plus, since #319, where it came from: `premium_coin` (paid to you), `buyback_coin` (paid to buy back), `fees_coin` (exchange fees, opening share + closing fee) — costs positive, `premium − buyback − fees = realised_coin` — and `premium_usd`, `buyback_usd`, `fees_usd` at each close's spot (they add up to `realised_usd`); `spot_start`, `spot_end`, `spot_days`, `hold_usd` are null here (filled by `/api/income`); `this_month` (= the last of `months`); `unrealised_coin`, `unrealised_usd` (open book at its marks); `coin`; `basis`; `summary` null (see `/api/income`).
  - `worst_case` — **a model, label it so**: `model` (the text to show), `available` (false with `reason` when spot or DVOL is missing — show "unknown", never 0), `sigmas` (3), `dvol`, `move_pct`, `coin`, and `down` / `up` each `{spot, loss_coin, loss_usd, pct_of_equity}` (positive = money lost; `pct_of_equity` null without the equity). Black–Scholes on each leg's current IV, one day passed, spot moved ±3 daily σ (σ = DVOL ÷ √365); `loss_coin` is the USD loss at the moved spot. `scenarios` (#318): the same repricing for −3, −2, 0, +2, +3 σ, worst fall first, each `{sigmas, move_pct (signed), spot, result_coin, result_usd, pct_of_equity}` — **signed results, + = gain** (the opposite sign of `loss_*`); ±3σ are exactly `down` / `up` negated, 0σ is one day of time decay (a gain for a short book); `[]` when not available. `pct_of_equity` is of Deribit's equity in the coin (the account summary the decision loop reads).
  - `environment` (live | testnet) and `stop_loss_multiple` (`stop_loss_multiplier`: a leg is bought back once it has lost this multiple of its premium) — for the worst-case page's badge and words.
  - `delta_exit_threshold` and `repair_cooldown_hours` (#322: the config's delta exit and the wait after a stop, in hours) and `strangle` — the "How it works" page's live numbers: the short strangle with both legs and the nearest expiry, null when none is held (`internal/api/howitworks.go`, pure `HowItWorksOf`): `strangle_id`, `expiry`, `spot` (USD), `put` / `call` each `{instrument, strike, qty, premium_coin (paid when sold), exit_line}`, `premium_coin` (both legs: the most it can earn), `break_even_low` / `break_even_high` (the coin's price at expiry where the coin-settled strangle neither earns nor loses: qty·K ÷ (premium + qty) for the put, qty·K ÷ (qty − premium) for the call; high null when the call cannot cost the whole payment), `exit_lines` (false with `exit_lines_reason` when no IV, no threshold or at expiry — then both `exit_line` are null) and `exit_lines_model`. `exit_line` is the coin's price at which the leg's Black–Scholes |Δ| (its IV, DVOL when missing, zero rate, today) reaches `delta_exit_threshold` — a model; the bot's delta exit reads Deribit's live delta.
  - `last_action` — null before the first trade, else the journal's latest open or close: `at`, `kind` (open | close), `instrument`, `option_type`, `qty`, `rule` (the journal's reason, e.g. `stop_loss`), `reason` in plain words (e.g. "Bought back the put: it lost twice its premium (stop-loss)"), `detail` (the rule's numbers), and for a close `pnl_coin`, `pnl_usd`; `spot` (#320: the coin's index price at the action, USD; omitted when the journal has none).
- `GET /api/performance?range=7d|30d|all` (#232; default `30d`, any other range → 400; in the proxy allow-list, readable by any signed-in role and the read-only service token; not shown on screen yet) is `internal/perf`'s summary of the bot's P&L history (`data/pnl_history.jsonl`, every recorded point, never a Deribit call). `all` starts at the first recorded point. Coin amounts are in the bot's underlying:
  - `label` — `live` or `testnet` (from `DERIBIT_ENV`): show it, so testnet figures are never read as live. `range`, `from`, `to`, `as_of`, `points`, `source`.
  - `net_pnl` (coin: change of the cumulative total, realised + unrealised net of fees, first point → last), `net_pnl_known` (false with no point), `net_pnl_usd` (at the window's last spot; null without a spot).
  - `equity` (coin, at the window start: Deribit's margin balance from the first line that carries one — a USD balance under cross collateral is converted at that line's spot; never computed from P&L), `equity_known`, `equity_reason` (why it is unknown, or where it came from). While equity is unknown **every percentage of equity is null** — `return_pct`, `return_usd_pct`, `excess_return_pct`, `max_drawdown.pct`, `worst_week.pct` — show "unknown", never 0.
  - Hold the coin: `hold_known`, `spot_start`, `spot_end`, `hold_return_usd_pct` (spot end ÷ start − 1), `hold_return_coin_pct` (0: a held coin stays one coin); `return_usd_pct` (the strategy in USD) and `excess_return_pct` (= `return_usd_pct` − `hold_return_usd_pct`) need both equity and spot.
  - `max_drawdown` `{coin (≤ 0), pct}`; `worst_week` `{known (false until the window holds 7 days), start, end, coin, pct}`.
  - Coverage: `days`, `days_covered`, `missing_days` (UTC dates `YYYY-MM-DD` with no point — listed, never filled in).
- `GET /api/income` (#319; in the proxy allow-list, any signed-in role; shown on the [income page](#income-page)) is `/api/summary`'s `income` completed with the P&L history (`data/pnl_history.jsonl` over the months shown; its own route because it reads months of raw points, while the summary is polled every second):
  - each month's `spot_start`, `spot_end` (the coin's first and last recorded spot in the month), `spot_days` (days between them) and `hold_usd` — the account's equity at the month's start (Deribit's margin balance, coin) × (`spot_end` − `spot_start`): what holding the coin alone did in USD; null with `hold_reason` when the month has no spot or no balance recorded. In coin, holding alone is 0 by definition.
  - `summary` — `from`, `to`, `label` (`live` | `testnet`), `source`; `total_6m` `{coin, usd}` (the realised months added); `equity` (coin at the window start, null when unknown) with `equity_note`, `return_pct` (`total_6m.coin` ÷ equity: "% more coin than holding"; null when equity is unknown); `average_month` `{coin, usd}` over the `active_months` with at least one close (null before the first close); `up_months`, `down_months`; `worst_month` `{month, coin, usd, spot_move_pct, spot_days}` (lowest realised coin; the move null when not recorded; null before the first close); `worst_week` `{known, start, end, coin, pct}` (`internal/perf`'s worst 7 days of the total, coin; `pct` of equity, null when unknown); `days`, `days_covered`, `missing_days` (listed, never filled in).
- `GET /api/strangles/payoff` (#391; in the proxy allow-list, any signed-in role; the [Positions page](#what-you-see), the overview's strangle cards and the payoff modal) is the payoff chart of every open strangle (`internal/api/payoff.go`, pure `PayoffOf(view, now)`, from the strategy's view — never a Deribit call). Coin amounts in `underlying`, prices and USD at today's `spot`:
  - `as_of`, `underlying`, `spot`, `dvol`, `model` (the label to show: "Black–Scholes on each leg's IV, zero rate"), `delta_exit_threshold`, `stop_loss_multiple`, `bot_net_delta` (the bot's net delta from the view, coin, short-signed) and `bot_net_delta_usd_per_1pct` (× spot ÷ 100), and `strangles` (ordered by slot DTE, then expiry; `[]` when nothing is held).
  - each strangle: `strangle_id`, `slot` `{dte, delta}`, `expiry`, `dte` (fractional days), `spot`; `legs` (short legs, put first): `position_id`, `instrument`, `option_type`, `strike`, `qty`, `premium_coin`, `mark` (coin per option), `iv` (fraction, 0 = unknown), `delta` (per option), `unrealised_coin`, `position_delta` (−Δ × qty, coin) and `position_delta_usd_per_1pct`, `stop_loss_mark`, `exit_line` (the price where |Δ| reaches `delta_exit_threshold` today — How it works' `ExitLinePrice`) and `stop_level` (the price where the leg's modelled mark reaches `stop_loss_mark`), each null when not computable; `missing` (`[{option_type, rule, reason}]` — the side a one-legged strangle lacks, with `held_legs`' rule and reason, "unknown: …" when none is reported).
  - `premium_coin` (what the legs were paid: the most it can earn), `unrealised_coin` / `unrealised_usd` (the book's P&L now, net of opening fees), `earned_pct` (unrealised ÷ premium × 100; null without a premium), `net_delta_coin` / `net_delta_usd_per_1pct`, `break_even_low` / `break_even_high` (the at-expiry payoff's zeros, as How it works; null when that side is not held or cannot lose the whole premium).
  - `today` (false with `today_reason`, "unknown: no implied volatility for <instrument>" / "no spot price" / "at expiry", when the today curve, exit lines and stop levels cannot be computed) and `points` (ascending price, 121 evenly spaced over ±3 daily σ beyond the outer break-evens, spot and strikes, plus the spot, strikes, break-evens themselves): `{price, expiry_pnl, today_pnl}` in coin — `expiry_pnl` the coin-settled payoff at expiry (premium − qty × intrinsic ÷ price, before fees), `today_pnl` the P&L if bought back now: the book's unrealised P&L moved by the model's change in each leg's value from spot (so at spot it is exactly `unrealised_coin`; null when `today` is false).
- `GET /api/explain?seq=<event seq>` or `?trade=<trade seq>` (#314; in the proxy allow-list, any signed-in role; no page uses it yet — the assistant's grounded input for "why did the bot do that") is the facts the journal recorded about one event (`internal/api/explanation.go`, pure `BuildExplanation`, from the in-memory recent events `/api/events` serves — never a file read or a Deribit call): `event` (as in `/api/events`, with `plain`), `rule` (the trigger, close reason, skip reason word, risk change or new trend), `detail` (the rule's numbers; a skip without one gives its skip reason), `market` (`as_of`, `spot`, `dvol`, `iv_percentile`, `gex_regime`, `gamma_flip`, `flip_buffer_pct`, `trend`, `sma_trend`, `gex_bias`, the option's `delta`, `bid`, `ask`, `mid` — 0/absent = not recorded; null when the line records no market), `related` (the same instrument's or slot's events within ±30 min, oldest first, each with `plain`; `[]` for a line that names neither, e.g. a risk change) and `source: "journal"`. - **Every page and every `/api` route needs a signed-in session** (below). The bots' APIs know nothing about it: they stay unpublished on the compose network and the monitor reaches them as before (with `BOT_ADMIN_TOKEN` for close and rebalance).

## Sign-in

People sign in at `/login` with a username and password; `proxy.js` sends every page without a session to `/login?next=…` and answers 401 on every `/api` route except `/api/auth/login`, `/api/auth/refresh` and `/api/auth/reset`; the `/reset` page (a reset link, below) opens without a session too. The close and rebalance routes check the person again themselves (Roles, below).

### Roles (#171, PRD §3)

| Action | admin | manager | user |
|---|---|---|---|
| See the monitor | ✓ | ✓ | ✓ |
| Manual close, manual rebalance (and its dry run) | ✓ | ✓ | — (403) |
| Create, edit and delete users; reset a password or issue a reset link (Users page, `/api/admin/users`) | ✓ | — (403) | — (403) |
| Read the audit trail (Audit page, `/api/admin/audit`) | ✓ | — (403) | — (403) |

`admin` satisfies `manager` satisfies `user` (`lib/auth/roles.js`). Checked on the server, in the route handlers — not by hiding buttons (a user still sees them; the route answers 403 `manager role required` and the bot receives nothing). **State-changing routes re-read the person from the database** (`requireRole` in `lib/auth/server.js` → `AuthService.actingUser`): the user must still exist, their **current** role must allow the action (else 403), and the access token's session (`sid`, its refresh token's SHA-256) must still be live (else 401). So a demoted manager is refused at once, and a deleted user or one signed out everywhere too — not 15 minutes later. Read routes trust the token. An access token from before #171 has no `sid`: its first close answers 401, the page refreshes into a new token and retries.

The route sends the person to the bot with the request — `"actor": {"user": "bob", "role": "manager"}` beside `BOT_ADMIN_TOKEN` — and the bot logs and journals it (the close's `actor` and `detail` "manual close from the monitor by bob (manager)", `rebalance_manual`'s `actor`). User management is in `AuthService` (`createUser`, `changeRole`, `resetPassword`, `deleteUser`, `signOutEverywhere`: never zero admins, never delete yourself, every change ends that user's sessions), behind the Users page below.

| Part | How |
|---|---|
| Users | SQLite (`sql.js`, WebAssembly — no native build in the image) in `data/monitor/auth.db` (`AUTH_DB_PATH`), a `monitor-auth` Docker volume per environment: stable and mvp have separate users. Table `users`: username (3–64 of `a-z 0-9 . _ -`, case-insensitive), argon2id hash, role `admin`/`manager`/`user` (enforced: Roles, above), email, created, last sign-in |
| Passwords | argon2id (`hash-wasm`; 19 MiB, 2 passes), at least 12 characters. An unknown user is checked against a dummy hash, so it takes as long as a wrong password and gets the same 401 `invalid username or password` |
| Access token | JWT HS256 (`jose`), 15 min, cookie `access_token_<env>` (`<env>` = `MONITOR_DEPLOYMENT`, so stable and mvp on one host keep separate sessions, #368; plain `access_token` without it; HttpOnly, SameSite=Lax, path `/`), signed with `AUTH_SECRET`; carries the user id, name, role and `sid` (its session) |
| Refresh token | 32 random bytes, only its SHA-256 stored, 14 days, cookie `refresh_token_<env>` on path `/api/auth`; reusable until logout (several tabs). A password change, a role change or a deletion ends every session of that user |
| Silent refresh | `lib/api.js` `apiFetch`: the monitor's own 401 (header `x-monitor-session: required`) → one refresh shared by every waiting request → one retry; when that fails the page goes to `/login` and comes back afterwards. A bot's 401 passed through a proxy route is shown as an error, never a sign-out |
| Password change | `POST /api/auth/password` `{"current", "next"}` (#212), the header's **Account ▾ → Change password** form (current, new, confirm; shows the 12-character rule before sending). Live session required (re-read like a state-changing route; no session → 401, the service token never reaches it), same-origin JSON only. `next`: at least 12 characters and not `current`, else 400 with the reason (`Too short: at least 12 characters`, …). A wrong `current` → 401 `Current password is wrong` and counts as a failed sign-in of that username (Lockout, below: 5 lock it for sign-in and for this route, which then answers 429). Success ends **every** session of the person, then opens a new one for this browser (new access and refresh cookies): other browsers' next refresh fails and they go to `/login`. Their access token, being a stateless JWT, still reads the monitor for up to 15 min; their close, rebalance and password change are refused at once (the session is gone) |
| Reset link | For a person who forgot their password, no e-mail needed (#307): an admin's **Reset link** on the Users page → `POST /api/admin/users/<id>/reset-link` → `{"url", "expires_at"}`, shown **once** with a copy button; the admin hands it over by any safe channel. 32 random bytes, only their SHA-256 stored (`reset_tokens` in `auth.db`: `token_hash`, `user_id`, `expires_at`, `created_by` = the admin, `created_at`, `used_at`), valid **30 min**, **single use**; a new link voids the person's older ones; deleting the person deletes their links; not for your own account (409). The person opens `/reset?token=…` (public; `<meta name="referrer" content="no-referrer">`; the token is dropped from the address bar), types the new password twice and sends `POST /api/auth/reset` `{"token", "next"}` (public, same-origin JSON, under the per-IP sign-in limit: 429 with `Retry-After`). `next` follows the 12-character rule (400 with the reason, the link stays usable); an unknown, used, expired or replaced link gets the one 400 `link expired or already used` and nothing changes. Success sets the password, marks the link used and ends **every** session of the person — they then sign in at `/login`; lockout is untouched. The admin's direct **Reset password** stays as it was |
| Lockout | 5 failed sign-ins for a username within 15 min lock it until 15 min after the last one (same 401); 20 sign-ins a minute per IP, then 429 with `Retry-After`. The username failures and locks are kept per environment in `auth.db` (`login_failures`, `login_locks`; failures older than 15 min are deleted at the next failure), so a restart or deploy of the monitor does not clear a lockout; the per-IP limit is short-lived and stays in memory (a restart forgets it) |
| Secure cookies | `Secure` except on plain http to `localhost`/`127.0.0.1` (the compose port), where a browser would drop them. Opened from another machine over plain http, sign-in cannot work: put TLS in front first |
| Service token | `MONITOR_API_TOKEN` (≥ 32 chars) as `Authorization: Bearer …` reads `GET /api/bots/*` without a session — the deploy health check, `promote.sh`, the SME agent and `stress_inputs.sh` use it (`env_monitor_token` in `scripts/env_lib.sh`). Never a page, a close or a rebalance |
| Logs | one JSON line per sign-in, failure (reason, `locked`), lockout, rate limit, sign-out, first admin, user change (`user created`, `role changed`, `password reset` with `event: password_reset`, `reset link issued` (with `expires_at`), `signed out everywhere`, `user deleted`, each with `by`), reset by link (`password reset by link`, `event: password_reset`, `via: link`, the person, `by` = the admin who issued it, IP; a refused link is a WARN `reset by link refused` with the IP only), password change (`password changed`, `event: password_changed`, or `password change failed`) and refused action, with username and IP — never a password, hash, token or `AUTH_SECRET` |
| Audit | `data/monitor/audit.jsonl` beside the user database (`AUDIT_PATH`; off for an in-memory database), append-only, owner-only: one JSON line `{time, action, username, role, …}` per `signed_in`, `sign_in_failed` (reason), `locked`, `signed_out`, `password_changed`, `password_change_failed` (reason `password` or `locked`), `user_created` (`to` = the role), `role_changed`, `password_reset` (an admin set another person's password, #306), `reset_link_issued` (with `expires_at`, #307), `user_deleted`, `signed_out_everywhere` (each with `target`; `username` and `role` are the admin's), `password_reset_by_link` (`username` and `role` are the person's, `by` the admin who issued the link, `ip`), the analytics retention lines `events_pruned`, `events_deleted`, `events_exported` and their `_failed` forms (counts only, never an event; see "Analytics"), `survey_answers_deleted` / `survey_answers_delete_failed` (counts only, never an answer), `analytics_consent_changed` (`consent` true or false) and `manual_close` / `manual_rebalance` (bot, position ids or dry run, the bot's status and, for a close, what it filled). Never a password, hash or token (nor a reset link). Admins read it on the Audit page (below) |

The first start with no users creates an admin from `ADMIN_USERNAME` / `ADMIN_PASSWORD` / `ADMIN_EMAIL`; later starts never touch existing users. The server exits at start (`instrumentation-node.js`) when `AUTH_SECRET` is missing or shorter than 32 bytes, or the database cannot be opened.

### Users page (#306)

`/admin/users`, linked as **Account ▾ → Users** for admins only — the link is a convenience, the routes decide: a manager or a user gets 403 from every one of them (`requireRole(admin)`, the person re-read from the database like close and rebalance). The page lists every person (username, role, email, created, last sign-in) and has an **Add user** form; each row changes the role, resets the password, signs the person out everywhere or deletes them, each after a confirmation that says what follows. Your own row cannot be deleted or reset (use **Change password**).

### Audit page (#308, #249)

`/admin/audit`, linked as **Account ▾ → Audit** for admins only (a manager or a user who opens it sees "Only an admin reads the audit trail" and no lines; the route answers them 403). Filters: person (who acted: the line's `username`), action (the known list, `lib/audit.js` `AUDIT_ACTIONS`), from / to (UTC days, inclusive). A table of time (BRT, `lib/time.js`), person, role, action, target or bot, and detail (every other field as stored, e.g. a close's `position_ids` and `status`, a rebalance's `dry_run`), newest first, 100 lines at a time with **Older** for the next page. Read-only: nothing on the page or the route edits or deletes a line.

| Route | Does | Refusals |
|---|---|---|
| `GET /api/admin/audit?user=&action=&from=&to=&before=&limit=` | `{"off", "entries", "skipped", "next_before"}`: the lines as stored, newest first; `limit` 1–1000 (default 100); `next_before` = the cursor (a byte offset) of the next, older page, `null` at the end. Reads `AUDIT_PATH` backwards in 64 KB chunks (`lib/auth/auditread.js`), never the whole file, and stops at a full page or at lines older than `from`. A line that is not a JSON object is skipped and counted in `skipped` (per page), never a 500; a missing file is an empty list; an in-memory user database has no trail: `off: true`, which the page says | 400 unknown action, a malformed day, `from` after `to`, a bad `limit` or `before` · 403 not admin |

## Analytics (#193)

Usage events from the event plan (`docs/product/analytics/event-plan.md`) — what a person looked at or did, **never an amount, size, price, instrument, secret or email**. Nothing leaves the machine: no third-party tracker, SDK or script.

- **Sender:** `lib/track.js` `track(event, props)` posts to the monitor's own `POST /api/events`, without waiting and without ever throwing. It sends nothing until `setAnalyticsConsent(true)`; "no" or not asked yet (the default) means nothing at all is sent. Events outside the plan are dropped in the page too. The session id is random (32 hex), new after 30 min without an event. No component calls it yet. The consent can be set through `/api/consent` (below), but no screen calls it: the consent notice waits for E13's prototype.
- **Consent (#363):** the person's own answer, on their row in `auth.db` (`users.analytics_consent`; null = never answered).

  | Route | Does | Refusals |
  |---|---|---|
  | `GET /api/consent` | `{"consent": true \| false \| null}` for the signed-in person (re-read from the database, `no-store`) | 401 no session |
  | `POST /api/consent {"consent": true \| false}` | stores it and answers `{"consent", "note"}`; audited as `analytics_consent_changed` (the person and the new value only). *No* stops collection at once (`/api/events` and `/api/survey` answer 403); the note says events already stored stay until the person asks for their deletion (the CLI below) | 401 no session · 403 cross-origin · 415 not JSON · 400 any other body (only the one boolean field) |
- **Survey answers (#363):** `POST /api/survey {"survey_id", "session_id", "codes": {…}, "text"?}` — signed-in, same-origin JSON ≤ 4 KB, consent yes (403 otherwise, every survey: `surveys.md` §1–§2 show their cards only with consent and §3 stores no exit answer without it until counsel answers C3), `ANALYTICS_SALT` set (503). `lib/analytics/surveys.js` checks it against `surveys.md`: a known `survey_id`; only that survey's codes (`nps`: `score` required, `reason_code` of the NPS codes; `answers`: `came_for`, `hardest_to_find`, at least one; `exit`: `reason_code` of the exit codes); `text` only on NPS or with the exit's `other`, ≤ 500 characters. Anything else is refused whole: 400, nothing stored, a WARN naming the field, never the value. The codes and text go to the `survey_answers` table of `auth.db` (user row id, `survey_id`, codes as JSON, `free_text`, `created_at`); the `survey_answered` event carries the codes only and passes the collector's allow-list. When the event cannot be written the answer is removed again (500). 204 when stored. No screen sends it yet.
- **Allow-list:** `lib/analytics/plan.js` — each event and the only properties it may carry (enums, flags, capped millisecond counts, help catalogue keys of letters and `_` only, so no number fits). `__tests__/events-plan.test.js` keeps it equal to the plan's tables: change the plan first.
- **Surveys (#297):** `survey_shown`, `survey_answered` and `survey_dismissed` carry codes only — `survey_id` (`nps`, `answers`, `exit`), `score` (the strings `0`–`10`), `reason_code`, `came_for`, `hardest_to_find`. A survey's free text never goes into an event; it is kept in `auth.db` beside the user (`survey_answers`, `POST /api/survey` above) and deleted with them. Wording, triggers, frequency caps and the legal review that must come first: `docs/product/analytics/surveys.md`. No survey is on screen yet.
- **Collector:** `app/api/events/route.js` stores an event only for a signed-in person (re-read from the database), same-origin JSON ≤ 2 KB, whose `users.analytics_consent` is yes (403 otherwise) and when `ANALYTICS_SALT` (≥ 16 chars) is set (503 otherwise). An unknown event, a property not in the plan or a value outside its rule is refused whole: 400, nothing written, a WARN log naming the field, never its value. 204 when stored.
- **Stored:** one JSON line per event in `data/monitor/events.jsonl` beside `auth.db` (`EVENTS_PATH`; off for an in-memory database), append-only, owner-only: `event`, `ts` (UTC, to the second), `user_id` (HMAC-SHA256 of the user's row id with `ANALYTICS_SALT`, 16 hex), `session_id`, `role`, `environment` (`stable`|`mvp`, from `MONITOR_DEPLOYMENT`), `app_version` (`MONITOR_VERSION`) and the event's properties. Never the username, email, IP, user agent or URL. Not read by the bot.
- **Retention (#296):** `lib/analytics/retention.js` keeps raw events `EVENT_RETENTION_DAYS` (395, 13 months; needs legal review, change it there only). The monitor prunes older lines when it starts and then every 24 h (`instrumentation-node.js`). Each run writes an `events_pruned` audit line with the kept and removed counts; a failure is an ERROR log and an `events_prune_failed` line. Every rewrite goes through `events.jsonl.tmp` (0600, fsync) and a rename, so a crash leaves the old file or the new one whole.
- **Deleting a user** deletes their events in the same step: the `user_deleted` audit line is followed by `events_deleted` with the count. If the events cannot be deleted (e.g. `ANALYTICS_SALT` unset while the file exists), the user is still deleted, the failure is logged at ERROR and audited as `events_delete_failed`, and the answer's `events_error` gives the CLI command to retry with `--row-id`. Their survey answers (codes and free text) go in the same step: `survey_answers_deleted` with the count; a failure is an ERROR log, a `survey_answers_delete_failed` line and `survey_answers_error` in the answer, and the monitor deletes the rows left without a user when it next starts.
- **Access and deletion requests:** run from the repository root with that environment's values (both are required: stable and mvp each have their own; `frontend/node_modules` must be installed):

  ```bash
  AUTH_DB_PATH=…/data/monitor/auth.db ANALYTICS_SALT=… node frontend/scripts/analytics-user.mjs export alice [--out FILE]
  AUTH_DB_PATH=… ANALYTICS_SALT=… node frontend/scripts/analytics-user.mjs delete alice
  AUTH_DB_PATH=… ANALYTICS_SALT=… node frontend/scripts/analytics-user.mjs delete --row-id 7   # a user already deleted
  ```

  `EVENTS_PATH` and `AUDIT_PATH` default to the files beside `auth.db`. An export writes a new 0600 file (default `analytics-export-<user>-<time>.jsonl` beside the events) and never overwrites one: the person's events, then one `{"record": "survey_answer", "survey_id", "codes", "text", "created_at"}` line per survey answer (#363). `delete` removes events only; survey answers go with the user's deletion. The CLI reads `auth.db` without writing it, so the monitor can keep running. It prints counts and paths only and writes an `events_exported` / `events_deleted` audit line (`username` = `cli:<host account>`). It does not change the person's consent: to stop collection they answer no, or the admin deletes the user.

## Assistant (#191, E10)

A help assistant behind the sign-in, API only (no UI yet: the chat waits for E10's prototype). It answers from the published help and the user's own bot journal, cites them, says "I don't know" otherwise, and never advises or forecasts — the answer contract is `docs/product/assistant/contract.md` (draft, needs legal review, L11/L12).

- **Flow** (`lib/assistant/service.js`): the question's best `HELP_PASSAGES` (6) passages of `content/help-index.json` (`lib/assistant/search.js`, the BM25 of `internal/helpkb`) and, with `bot`, that bot's last 20 journal events from its `/api/events` (each a passage `journal:<bot>/<seq>` holding its plain-words sentence) go to the model (`lib/assistant/model.js`, Claude through the Messages API, `claude-haiku-5-5` unless `ASSISTANT_MODEL`; answer as JSON `{answer, citations}`). When no passage matches and no journal was asked for, the reply is "I don't know" with no model call. Then the guard (`lib/assistant/guard.js`, the twin of `internal/assistant/guard`) checks the answer: **no citation → "I don't know"**; an unknown citation, a number in no cited passage, advice or a forecast → the fallback reply. A bot that does not answer leaves the help alone as the source (WARN log).
- **Twins of the Go code:** `lib/assistant/phrases.js` copies `internal/assistant/guard/phrases.go` (`__tests__/assistant-parity.test.js` fails when they differ: change both); `__tests__/assistant-guard.test.js` runs the Go guard's cases and the golden set on the JS guard; `__tests__/assistant-search.test.js` scores the JS search on `tests/testdata/helpkb_questions.yaml` against `helpkb_baseline.json`.
- **Review log:** `data/monitor/assistant.jsonl` beside `auth.db` (`ASSISTANT_LOG_PATH`; off for an in-memory database), append-only, owner-only. One `"kind": "answer"` line per question — `id`, `ts`, `user`, `role`, `bot`, `question`, `sources` (passage ids given to the model), `model`, `model_answer` (the model's own text), `citations`, `verdict` (the guard's findings), `outcome`, `answer` (what was shown), `flag: false` — and one `"kind": "flag"` line per flag (`id`, `ts`, `user`, `role`, `note`); the answer line is never rewritten. An answer that cannot be logged is not shown (500). The monitor's stdout gets one line per question with the id and outcome only.

| Route | Does | Refusals |
|---|---|---|
| `POST /api/assistant` `{"question", "bot"?}` | `{"id", "answer", "citations": [{id, source, title}], "outcome", "ai_generated": true, "notice"}` — `outcome` `answered` \| `dont_know` \| `refused` \| `no_citation` \| `rejected`; `citations` only for `answered`; `notice` the AI label (avisos.md's fixed notice), to show with every answer | 401 no session · 403 cross-origin · 415 not JSON · 400 no question, over 500 characters, `bot` not a string · 404 unknown bot · 413 body over 2 KB · 429 over `QUESTIONS_PER_HOUR` (30) per person, with `Retry-After` (in memory) · 502 the model failed (logged) · 503 no `ANTHROPIC_API_KEY` |
| `POST /api/assistant/flag` `{"id", "note"?}` | 204: a flag line for that answer | 401 · 403 cross-origin, or someone else's answer (the person who asked, a manager or an admin may flag) · 400 no id, a note over 500 characters · 404 unknown id |

### Glossary (#188)

`content/glossary.json` holds one short tip for every term the monitor shows and every config setting: `{ "<term>": { "short" (≤ 140 chars), "long" (≤ 600), "risk_income" (how it moves risk and income), "source" ("OptionStrategy.md#<anchor>" or "frontend/README.md#<anchor>"), "labels" (optional: the exact monitor texts that mean this term) } }`. Config keys are entries under their YAML name, nested ones as `parent.child` (`backtest.fill_model`). `lib/glossary.js` `findTerm(label)` finds an entry by term, config key or label. It is content only: the tips UI (E11) and the assistant (E10) will read it.

Tests keep it complete: `__tests__/glossary.test.js` fails when a literal column header (`<th>`), `<dt>`, `label="…"` prop, hold-rule, feed-event or exit-reason label in the monitor, or a key of `config_btc.yaml`/`config_eth.yaml`/`config_btc.mvp.yaml`, has no entry, when a source anchor does not exist, and on return promises; `tests/glossary_test.go` checks every key `config.Load` accepts. **A new column or setting needs its entry in the same PR.** Writing rules: short sentences (8th-grade reading), no jargon without its own entry, no return promises. **Plain-words checks (#339, `test/plainWords.js`):** the `short` text has at most 25 words a sentence (the long texts keep the 35-word limit above), and a jargon word (*delta, gamma, theta, vega, strangle, IV, DVOL, GEX, margin, strike*) may appear in a text only if it is a glossary key or label, or the entry defines it (`implied volatility` spells out "IV"). A test failure names the entry and the word. An entry that must use an undefined jargon word goes in `JARGON_ALLOWED` in `__tests__/glossary.test.js` with the reason.

### Risk notes before confirming (#299)

`content/confirm-notes.json` says in plain words, before a person confirms, what a manual close or a rebalance does, what can go wrong and what the bot does next: `{ "manual_close": { "does", "risks", "follows", "follows_last_leg", "terms", "source" }, "rebalance": { "does", "risks", "follows", "dry_run", "terms", "source" } }`. `terms` lists the glossary keys the texts name (settings by their YAML key, e.g. `repair_cooldown_hours`), so each can link to its tip; `source` is an `OptionStrategy.md#…` or `CLAUDE.md#…` anchor. `lib/confirmNotes.js` `noteFor(action, { lastLeg, dryRun })` picks the texts: `lastLeg` (manual close of a strangle's last leg) gives `follows_last_leg`; `dryRun` (rebalance preview) gives `dry_run` as `does` and no risks or follows, since nothing is sent. Content only: the confirmation dialogs read it once their prototype is approved (E11). `__tests__/confirm-notes.test.js` keeps every text ≤ 280 characters, free of figures (no digit at all) and of forecast, advice and promise words, every named term a glossary key and every source anchor real. The facts follow `internal/strategy/manualclose.go` and `manualrebalance.go`: **a rule change there needs its note changed in the same PR.** This is risk-disclosure wording drafted against `docs/legal/`: it may be shown to the team's own users, never to an external user before counsel approves it.

### Empty states (#298)

`content/empty-states.json` holds, for every panel, chart and list the monitor renders, one sentence per state: `{ "<panel>": { "empty", "loading", "stale", "error" (each ≤ 140 chars), "source" ("OptionStrategy.md#<anchor>" or "frontend/README.md#<anchor>") } }` — what will appear there, when, and why it is not there now. Facts only, in the bot's plain-words style (`internal/api/explain.go`): never a forecast or advice. The keys are the collapsible panels' `monitor.panel.*` storage keys plus `monitor.header`, `monitor.gex`, `monitor.summary`, `monitor.kpi`, `monitor.positions`, `monitor.activity`, `monitor.pnl`, `monitor.pnl_coin` and `monitor.orders` (`PANELS` in `lib/emptyStates.js`); `emptyStateFor(panel, state)` returns the sentence or null. Content only: the screens do not read it yet (E11's prototype first).

`__tests__/empty-states.test.js` (checks in `test/emptyStateChecks.js`) fails, naming the panel, when a `storageKey` or `<Panel title>` in `components/Monitor.jsx` has no key, when a key lacks a state, when a text is over 140 characters, on a forecast or advice word (deny-list: *will earn*, *guaranteed*, *should buy*, …) and when a source anchor does not exist. **A new panel needs its entry in the same PR.** The same plain-words checks apply (#339): at most 25 words a sentence, and no jargon word without a glossary entry; the failure names the panel, the state and the word.

The inventory of every panel's conditions, with the copy and the API field that tells each one apart, is `docs/product/education/empty-states.md` (#250); `__tests__/education-docs.test.js` keeps its copy equal to this catalogue, so change the JSON first and copy the sentence there.

### How-to videos and the comprehension test (#337, #338)

`docs/product/education/video-storyboards.md` holds the script, shot list, captions, glossary terms, risk sentence and source anchor of each how-to video (30–90 s, one task each; ids `video.<task>` are the analytics catalogue ids of `video_played` / `video_completed`, letters and `_` only). Content only: nothing is recorded or shown in the monitor yet; the player and the links where each task happens wait for the E11 prototype, and any public video with performance figures needs legal review. `__tests__/video-storyboards.test.js` checks every section (length, numbered shots, captions equal to the spoken text, at most 200 spoken words, a risk sentence, an existing source anchor, glossary terms that exist, no amount, no promise). `docs/product/education/comprehension-test.md` is the protocol that tests tips and videos with five real people; results stay under `data/product/`.

Stack: Next.js (App Router) · Tailwind CSS v4 with design tokens in `app/globals.css` (`profit`, `loss`, `call`, `put`, `live`, `testnet`…) · Recharts · clsx.

## Rules of the road

- **Read-only.** Anything that would change trading state (pause, kill switch, parameter edits) needs authentication, an explicit confirmation step and an audit entry, and must reuse the bot's existing code paths — it is a planned phase, not part of this page.
- **Never expose it publicly.** It shows positions and P&L; Docker binds it to `127.0.0.1`. Sign-in protects it from anyone who reaches the port, but it is no substitute for TLS and a closed port.
- Every number carries its unit (BTC/ETH, USD, %); missing data shows "—", never 0; stale data is flagged.
- No business logic in Next.js routes — the Go bot is the single backend. The one exception is the monitor's own users and sessions (`lib/auth/`).
- **Times: stored in UTC, shown in BRT.** The bot, its journal, history files and API are UTC; the page converts only for display, in one place (`lib/time.js`, `America/Sao_Paulo`, UTC−3). Change the zone there, never in the data.
