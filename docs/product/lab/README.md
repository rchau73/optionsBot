# Strategy-change lab (E9)

A manager's parameter change is studied offline before anyone decides on it:

1. `cmd/compare` (#186, #301) runs the current and the proposed settings through the backtest, the replay of the recorded books and the stress shocks → `data/compare/<time>/report.md|json`.
   `-neighbours <key>` (#495) adds the fragility check: the proposed config re-run with that setting at −20 %, −10 %, +10 % and +20 % (rounded to the catalogue's step, clipped to its range; a value `Validate` refuses is skipped with the reason) and the return, worst week, drawdown and fees of each.
   A cliff is flagged where the worst week or drawdown moves by more than 1 pp of equity between adjacent values or the return flips sign (`compare.CliffPP`, its reason in `internal/compare/neighbours.go`).
2. `cmd/analyze` (#426) asks the model for a plain-words analysis of that `report.json`, checked number by number against it (`internal/aianalysis`, contract in `docs/ai-analysis.md`, #257) → `analysis.md|json` beside the report, or nothing when the check fails.

3. The monitor serves the runs read-only to managers and admins (#539, `frontend/docs/users-and-roles.md`): `GET /api/lab/runs` lists them newest first with the settings changed and the headline numbers in percentages (return, worst week, drawdown, fees), each labelled "backtested, not a forecast"; `GET /api/lab/runs/<id>` returns one run with its `report.json`.
   The AI analysis is not served: `analysis` says "withheld pending legal review" until counsel answers legal question L10 and the constant `L10_ANALYSIS_GATE_OPEN` (`frontend/lib/lab.js`) is changed in a reviewed PR.

4. Before a run, `POST /api/lab/validate` (#586, managers and admins) says whether a proposed value may be tried: the range, step and unit from the catalogue, the cross rules `Validate` enforces against the shipped config, whether it is a core policy (a new default needs the product owner), the tip and the current value.
   Its data, `frontend/content/lab-settings.json`, is generated by `go run ./cmd/paramdocs` with `docs/parameters.md`, and `tests/lab_settings_test.go` loads each bound through `config.Load`, so it cannot drift from the bot; the check applies nothing.
   The margin bands' list rules (lowest band at 0, no two bands at one percentile) are listed and flagged not checked, since one value does not say which band it replaces.

5. A manager asks for a run through `POST /api/lab/requests` (#641, managers and admins): each proposed value is checked like `POST /api/lab/validate`, and a refused one queues nothing.
   A valid request is a small file in the private queue `data/compare/requests/` (id, requester, time, underlying, values, status `queued`; no secret, no amount), with an audit line `lab_request` naming the person and the keys.
   The runner, `scripts/lab_runner.sh` (`cmd/labrun`), takes one request at a time (a lock folder: never two runs together) and runs `cmd/compare -base config_<coin>.yaml -set <key>=<value> … -neighbours <the first number>` over the last 7 whole UTC days, with the recorded books and the captured stress book when they are there.
   `-set` (#641) builds the proposed config as a temporary copy of the base with only those values (`compare.WriteWith`), removed after the run; the report's `proposed` reads "config_btc.yaml with gamma_flip_buffer_sd=1.2".
   The status goes `running`, then `done` with the report's id (`run_id`) or `failed` with a short reason, and the queue moves on; a request still queued a day after it was made is `expired`, one a stopped runner left `running` is `failed`.
   Each person may have 3 requests waiting or running.
   `GET /api/lab/runs` lists the requests without a report yet under `requests`, with their status; a done run is a row of `runs` as before.
   `cmd/analyze` still runs by hand on the report, and its analysis stays withheld behind `L10_ANALYSIS_GATE_OPEN`.
   Run the runner from the environment the monitor reads (its `data/compare` is the monitor's `COMPARE_DIR`), by hand or from cron.
   Metrics from the queue files alone (ids and times, no values): the share of requests that end `done`, the median minutes from `requested_at` to the done `updated_at`, and requests per manager per week.

6. `GET /api/lab/runs/<id>/preview` (#682, managers and admins) says what confirming a finished run would change, and applies nothing: each setting with its title and tip, the account's value and the proposed one, the account (one at a time, decision of 2026-10-20), the person, the numbers labelled "backtested, not a forecast", the fragility flags, and the text of the audit line.
   `needs_product_owner: true` (a core policy, or a key the catalogue does not know) or `stale: true` (the run is over 7 days old, the value it started from is not the account's, the account's value cannot be read, or the proposed value is now refused) gives `confirm_token: null`, and so does a run with no numbers for the proposal; `reasons` says why in plain words.
   The 7 days are `PREVIEW_MAX_AGE_DAYS` (`frontend/lib/labpreview.js`): the runner compares the last 7 days, so an older run has no day in common with the week after it.
   "The account's value" is the shipped config in `frontend/content/lab-settings.json` until E8's tenancy gives a real one; mvp's BTC runs `config_btc.mvp.yaml`, which differs only in `gex_direction`, a core policy that never gets a token.
   The token is an HMAC, under `AUTH_SECRET`, of the run, the person, the account, both values and the 5-minute window it was issued in, so the confirm can recompute it and see that what is confirmed is what was shown.
   Reading a preview writes one audit line, `parameter_change_previewed`, naming the person, the account, the run and both values; a refused call writes none.

7. `POST /api/lab/runs/<id>/apply` `{"confirm_token"}` (#741, managers and admins) records the confirmed change, and applies nothing.
   The server recomputes the preview and refuses a token for another run, person or value, one over 15 minutes old (`CONFIRM_TOKEN_MINUTES`), a core policy (it names the product owner as the approver), a stale or out-of-range value, a run whose request is not done and a run already recorded (a token is used once).
   Success writes `data/compare/applied/<id>.json` once and one audit line, `parameter_change_recorded` (the person, the account, the run, old → new, the token's id), and answers `applied: false, recorded: true`, with the numbers labelled "backtested, not a forecast" and the risks beside them.
   **How a recorded change reaches the running bot is not decided** (a reviewed config PR and a restart, or a later hot-reload story): it needs a person's decision, with E8's tenancy (links of managers to accounts; until then a manager confirms for every account) and the legal answer on advisers (PRD §11, L10).
   Until then the record is the whole effect: no config file is written, no bot restarted, no order placed.

No page shows them yet: that waits for E9's UI prototype. The AI never changes a setting, and neither tool, route, queue nor runner applies one: a change takes effect only after a manager confirms it.
